# 非機能要件

## 6. 非機能要件

### 6.1 セキュリティ
| 項目 | 要件 |
|---|---|
| 認証 | Better Auth のメールアドレス + パスワード認証。セッションは DB に保存し Cookie で受け渡す。パスワードは Better Auth の標準方式(scrypt)でハッシュ化する |
| 認可 | 閲覧(一覧・詳細・検索・ユーザーページ・コメント表示)はゲストも利用可。投稿・お気に入り・コメント投稿はログイン必須。レシピとコメントの編集・削除は投稿者本人かどうかを**必ずサーバー側(service 層)で**確認する。画面でボタンを隠すだけにしない |
| CSRF | 更新処理は Server Actions(POST のみ。Next.js が Origin と Host の一致を確認する)で行い、GET で状態を変えない。認証エンドポイントは Better Auth の Origin 確認を有効にする。セッション Cookie は `SameSite=Lax` |
| XSS | 料理名・材料・手順・コメントは文字列として表示し、HTML として解釈しない(`dangerouslySetInnerHTML` を使わない) |
| 入力検証 | 文字数・必須・件数などはフロントとサーバーの両方で検証し、サーバー側の検証を正とする |
| 画像アップロード | 形式はファイルの中身(先頭バイト)で判定し、4MB を超えるものは受け付けない(本番の Vercel はリクエスト本体が 4.5MB までのため)。保存時のファイル名はサーバーで採番し、利用者が付けた名前は使わない |
| ログイン試行 | Better Auth のレート制限で、ログインは同じ接続元から 1分 10回までとする(総当たり対策) |
| ログ | パスワード・セッショントークンはログに出さない |
| 秘密情報 | DB の接続情報・認証の秘密鍵・ストレージの鍵は環境変数で渡し、リポジトリに入れない。`NEXT_PUBLIC_` で始まる環境変数に秘密情報を入れない |
| 本番通信 | デプロイ時は HTTPS のみとし、セッション Cookie に `Secure` / `HttpOnly` / `SameSite=Lax` を付ける |

### 6.2 データの整合性
- レシピと材料・手順の登録・更新は1つのトランザクションで行い、一部だけ保存された状態を作らない。
- お気に入りは DB の一意制約 `(user_id, recipe_id)` で重複を防ぐ。
- レシピを削除したら、材料・手順・お気に入り・コメント・写真ファイルも削除する(写真ファイルの削除に失敗してもレシピの削除は完了させ、ログに残す)。

### 6.3 性能
| 項目 | 目標 |
|---|---|
| サーバー処理の応答時間 | 想定規模(ユーザー100人・レシピ1,000件)で、ページのデータ取得と Server Actions の 95% が 500ms 以内 |
| 一覧・検索 | 1回 20件。投稿者名・お気に入り数・自分が保存済みかを含めて取得し、N+1 クエリを発生させない |
| キーワード検索 | 部分一致検索に耐えるインデックス(PostgreSQL の `pg_trgm`)を使う |
| 画像 | 一覧ではサムネイル表示用に縮小した画像を使う(`next/image` を使うか、保存時に縮小するかは設計時に決める)。初回表示がスマートフォンの通常回線で 3秒以内 |

### 6.4 ユーザビリティ・対応環境
- スマートフォン(幅 375px〜)と PC(幅 1280px 程度)の両方で崩れずに使える(レスポンシブ)。料理中にスマートフォンで見ることを想定し、詳細画面の材料・手順は大きめの文字で表示する。
- 対応ブラウザ: 最新版の Chrome / Safari / Edge。
- 投稿・削除などの操作結果は画面上に短いメッセージで知らせる。通信エラー時は入力内容を消さない。
- 主要なボタン・入力欄にはラベルを付け、画像には代替テキスト(料理名)を付ける。

### 6.5 保守性・品質
- 画面・Server Actions(`app/`)、業務ルール(`lib/services/`)、DB アクセス(Prisma)の層に分ける。TypeScript は `strict: true` とし、`any` を使わない。
- 入力検証、検索条件の組み立てには単体テストを書く。編集・削除の権限確認、お気に入り、一覧・検索は、本物の PostgreSQL につなぐ統合テストで確かめる(行ロック・SQL の条件まで含めて確かめるため)。
- 投稿 → 検索 → お気に入りの一連の流れは Playwright の E2E テストで確かめる(手元で実行)。
- GitHub Actions で Pull Request ごとに型チェック・ESLint・単体テスト・ビルドと、統合テスト(PostgreSQL のサービスコンテナ)を実行する。
- サーバーのログは JSON 1行形式で書き出し、パスワード・トークン・Cookie などのキーの値は伏せる(`lib/logger.ts`)。捕まえられなかったエラーは `instrumentation.ts` の `onRequestError` で記録する。
- Server Actions の失敗は `{ ok: false, code, message }` の形に統一し、原因(入力エラー / 未ログイン / 権限なし / 存在しない / 重複 / サーバーエラー)を区別できるようにする。存在しないレシピのページは 404 を返す。想定外のエラーは画面にエラー表示を出し、詳細はサーバーのログにだけ残す。

### 6.6 運用
- 課題提出・発表の期間中に動作するデモ環境を用意する(Vercel + Supabase。[技術スタック](05-tech-stack.md) 11.5 を参照)。
- バックアップ・監視は課題の範囲外とする(デプロイ先の標準機能に任せる)。
